## 2. 项目概述

### 2.1 背景与问题

内部人员通过同一工作空间处理目标与复盘、客户经营、项目交付、产研任务、培训和组织配置。现有导航与历史综合 PRD 的功能清单不完全一致，业务入口中既有完整交互，也有演示或待核实的数据与权限规则。本稿首先解决“界面做什么、谁可操作、看哪些数据、异常时如何反馈”的沟通缺口。

### 2.2 目标与价值

| 类型 | 目标 | 可观察结果 |
| --- | --- | --- |
| 员工效率 | 从待办、目标、复盘和协同进入自己的工作 | 能识别当前责任、办理入口和保存结果 |
| 管理协作 | 主管查看部门目标、成员复盘及进度 | 部门与个人数据不混用，审核和汇总有明确边界 |
| 业务连续性 | 客户、项目、产研、培训和配置入口形成可追踪流程 | 列表、详情、编辑、异常和返回路径一致且可验收 |
| 产品治理 | 把已核实能力与未决规则区分 | 每项待补充内容有具体问题，不以假设填充权限或字段 |

### 2.3 现状对照与范围决策

现有项目包含六个一级导航组；旧综合 PRD 记载了当前菜单之外的综合中心、更多 CRM 页及其他历史功能。本稿仅把**当前导航可见的三十个入口**纳入主功能清单；应用内可抵达但不在侧栏的知识页面单列，历史文档或兼容入口暂不算当前主导航。竞品对照及统一原型尚未提供，待补充：选定参照产品和对比维度；确认人：待指定；计划确认时间：待确定。

### 2.4 产品边界

- 面向内部登录用户；部分培训管理、目标设置及业务编辑能力另有角色/权限判断。侧栏入口当前可见不代表所有角色均可修改或查看全部数据。
- 覆盖当前导航、其实际打开的页面以及用户完成主要流程所需的弹窗、抽屉、详情和页签。
- 本项目按前端交互与现有演示持久化能力验收；文档不虚构正式业务接口、数据库能力、离线提醒或跨系统数据同步。
- 不把当前未展示的历史功能删除或宣布废弃；其产品归属与重新开放条件单列待确认。

| 事项 | 原因及处理方式 |

### 3.4 版本与依赖

本稿不新增版本号或发布时间。已有版本需求与历史变更继续由既有文档维护；如产品确认现状差异，应在相应版本需求中单独决策。前置依赖是实际人员角色、数据权限范围和统一原型的产品确认。

## 4. 业务流程与状态流转

| 场景 | 主要流程 | 当前可观察的边界 |
| --- | --- | --- |
| 日常工作 | 登录 → 我的任务 → 进入对应工作项/协同/审批 → 返回待办 | 未登录返回登录；数据加载失败可重试；待办按当前人员展示 |
| 目标制定 | 选周期与范围 → 创建/承接 → 保存草稿或提交 → 按配置确认 → 生效/退回 | 草稿不直接生效；确认人受组织关系与配置影响；无权限不能保存 |
| 复盘总结 | 选周报/月报 → 编辑 → 草稿/提交 → 查看历史；逾期按配置补录 | 已提交周期避免重复；主管部门报告须核对本轮员工提交与已读；失效目标阻止错误提交 |
| 协同事项 | 发起类型 → 选择归属及负责人 → 流转/转派/转任务 → 验收或关闭 | 不同类型字段与关闭条件不同；具体状态字典按现有配置核对 |
| 产品交付 | 产品 → 迭代/工作项 → 测试与缺陷/版本评审 → 项目交付查看 | 产品范围影响任务候选；阶段与已归档数据不应混入有效列表 |
| 培训 | 课程 → 章节学习 → 个人进度/考核；管理员维护课程与台账 | 非管理员进入培训管理显示无权限状态 |

跨模块更新失败时不应以成功提示代替保存结果；待核的并发与部分成功策略在对应界面保留待补充。状态显示、回退及历史快照依业务对象分别描述，不把“已提交”等同“已生效”。

| 角色或身份 | 当前已核实的能力 | 数据范围 | 待补充 |

| 已登录内部用户 | 可进入当前侧栏页面；具体写入能力随业务页面变化 | 不等于全部数据权限 | 菜单级授权与各业务模块角色表；确认人：待指定；时间：待确定 |

**权限解释**：界面入口、按钮呈现、可见数据、可修改数据是四项独立判断。仅当具体子界面已核实时写确定范围；未核实的范围不能写“全部”。角色撤销、人员失效或记录状态变化时，提交动作须再核对权限；该行为未核实的模块标待补充。

下表按当前导航逐项区分可见和可修改；“待补充”不是默认允许，也不代表默认拒绝，涉及正式权限决策统一追踪 Q-02、Q-03。若界面只有查询，“无”仅指**该界面当前没有写入入口**，不推断其他业务页面也无权修改。
