# OKR 逐级承接与拆解设计

## 1. 目标与范围

将当前 OKR 页面从“目标记录 + 动作记录”的平行编辑模式，调整为面向真实组织关系的递归目标树：组织根目标 O 下可以有多个 A；每个 A 可以被一个或多个主管承接并继续拆解；下级动作可以继续产生下级动作，形成任意深度的 `O -> A -> A -> A` 关系。

本设计覆盖目标与动作的创建、草稿、提交、只读详情、承接关系、权限、撤回/调整、递归展开和进度汇总。不改变复盘、绩效报告和非 OKR 工作项的业务含义。

## 2. 核心业务规则

### 2.1 节点与关系

- O 和 A 统一为目标节点，节点类型为 `objective` 或 `action`。
- 根 O 没有父节点；根 O 下的第一层 A 通过 `parentNodeId` 指向 O。
- 每个下级动作只能有一个直接父节点，因此树上的路径唯一。
- 同一条 A 可以被多个主管承接，但不复制 A；通过独立承接关系记录每个主管的承接分支。
- 承接关系只决定“谁可以看到并继续拆解该节点”，不改变节点的唯一身份。
- 动作可以不指定下级承接人；未指定承接人时动作仍然保存并可由当前责任人跟踪。

### 2.2 逐级可用性

- 老板先创建并提交公司 O 及其直属 A。
- 主管只有在上级 A 明确指派给自己后，才显示该 A 的拆解入口。
- 员工只有在主管 A 明确指派给自己后，才显示该 A 的拆解入口。
- 没有上级指派来源时，不显示“拆解动作”空表单，只显示无可拆解目标的空状态。
- 当前用户创建的动作不能自动变成自己的上级入口，必须存在真实的父节点与承接关系。

### 2.3 状态与修改

每个节点使用独立状态：`draft`、`submitted`、`active`、`withdrawn`、`adjusting`。

- 草稿：创建人可编辑、删除、调整顺序、修改承接人和继续添加下级动作。
- 已提交/已生效：默认只读，展示承接进度和下级完成进度。
- 撤回修改：只能由有权限的创建人或组织管理员发起，生成可追踪的调整版本，不覆盖已提交历史。
- 创建调整：从已提交节点创建新版本，原节点保持历史只读，新版本提交后替换当前有效版本。
- 撤回、作废和调整必须记录操作人、时间、原因和前后版本号。

### 2.4 指派规则

- 一个 A 可以指派给多个主管，共享同一个来源 A。
- 默认推荐老板指派部门主管，再由主管向员工拆解。
- 老板直接指派普通员工时，标记为“跨级指派”，同时通知该员工的直属主管。
- 每条承接关系包含来源节点、被指派人、指派人、指派层级、是否跨级、当前状态和通知状态。
- 同一来源节点对同一用户只能存在一条有效承接关系；历史撤销关系保留审计记录。

### 2.5 进度汇总

- 有直接子动作时，父级进度按直接子动作权重加权平均。
- 子动作先递归计算自身进度，再参与父级计算。
- 没有子动作时，使用节点自身进度。
- 权重为空或为零的子动作不参与加权分母，但必须展示配置异常提示。
- 父级汇总进度为只读值，不能通过编辑父级节点手工覆盖。
- 汇总结果应返回参与计算的子动作数量、已完成数量、权重总和和异常数量。

## 3. 页面与交互

### 3.1 添加目标编辑页

面向老板或组织根负责人。创建公司 O，维护直属 A、权重、截止时间和承接人。支持保存草稿、提交、删除草稿、调整 A 顺序。提交前校验 O 标题、至少一个有效 A、权重合计和承接关系。

### 3.2 添加目标草稿详情页

展示当前用户创建的草稿 O/A。允许继续编辑、删除节点、调整排序和修改承接人；提交时只提交当前草稿版本。提交失败保留编辑内容和校验错误。

### 3.3 添加目标已提交详情页

只读展示 O 及直属 A，默认展开到第二级。每个节点显示负责人、状态、截止日期、进度、下级数量和承接完成度，例如“2/3 个承接分支已拆解”。点击节点打开右侧抽屉，展示详情、来源、承接人和操作历史。提供“撤回修改”和“创建调整”，不提供静默编辑。

### 3.4 拆解动作编辑页

面向主管或员工。页面只展示系统自动读取的可承接来源 A，不允许重新选择或修改来源 O/A。表单创建当前用户的下级 A，可选择一个或多个承接人，也可以不选择承接人。支持保存草稿、提交、继续添加同级动作和调整动作顺序。

### 3.5 拆解动作草稿详情页

只展示当前用户创建的草稿动作及其来源链路。允许编辑、删除、修改承接人和提交；保存时更新原草稿节点，不重复创建记录。来源节点变更或被撤回时，显示阻断提示并禁止提交。

### 3.6 拆解动作已提交详情页

默认只读，显示完整来源路径、当前节点、直属下级、下级承接情况和递归进度摘要。树默认展开到第二级；点击展开按钮按节点加载下一层，支持“全部展开”。右侧抽屉展示节点详情和审计记录。调整必须走撤回或新版本流程。

### 3.7 通用状态

所有列表、节点行、抽屉和操作按钮提供 Normal、Hover/Focus、Active/Loading、Disabled/Error 四种状态。加载下一层时只锁定当前节点，不阻塞整棵树；空来源、权限不足、来源失效、网络错误和并发冲突均保留页面上下文并提供重试或返回入口。

## 4. 数据契约

### 4.1 GoalNode

```text
id
tenantId
periodKey
kind: objective | action
parentNodeId: nullable
rootNodeId
ownerId
creatorId
title
payload
weight
selfProgress
aggregatedProgress
status
version
sourceVersionId: nullable
createdAt
updatedAt
submittedAt: nullable
```

`payload` 仅承载节点自身的业务字段，不再承载父子关系、完整树或承接权限。父子关系使用 `parentNodeId`，承接使用独立关系表。

### 4.2 GoalAssignment

```text
id
sourceNodeId
assigneeId
assignedBy
assignmentLevel: supervisor | employee
crossLevel
status: active | revoked | completed
notifiedAt
revokedAt: nullable
createdAt
```

### 4.3 GoalNodeSummary

```text
nodeId
directChildCount
expandedChildCount
completedChildCount
assignmentCount
completedAssignmentCount
weightTotal
aggregatedProgress
progressWarnings
hasMoreChildren
```

## 5. API 方向

保留现有 OKR 入口兼容层，新增按节点语义组织的接口：

- 查询当前用户可见的根节点和摘要。
- 按节点分页查询直属子节点。
- 查询节点详情、来源链路和承接关系。
- 创建、更新、删除草稿节点。
- 创建、撤回、撤销和提交承接关系。
- 提交节点、创建调整版本、撤回当前版本。
- 查询递归进度摘要和下级承接统计。

所有写操作都必须校验租户、当前版本、节点状态、来源状态和用户权限；并发冲突返回明确的刷新后重试提示。

## 6. 权限与一致性

- 服务端是可见性和父节点合法性的唯一判定来源，前端隐藏按钮不构成权限控制。
- 创建下级动作时，服务端校验当前用户拥有有效承接关系，且父节点仍处于可承接状态。
- 已提交节点不可直接更新；撤回/调整必须生成事件和新版本。
- 删除仅允许删除未提交草稿；存在有效下级节点或承接关系时不得物理删除，改为撤销并保留审计。
- 同一父节点下的排序使用稳定序号和版本校验，避免并发调整覆盖。

## 7. 迁移策略

1. 为现有 OKR 记录建立统一节点映射，根 O 和现有动作均生成节点 ID。
2. 将现有 `parentObjectiveId`、`parentActionId`、`parentKeyResultId` 转换为 `parentNodeId`。
3. 将 payload 中的 `assigneeId/assigneeIds` 转换为 GoalAssignment，保留原 payload 字段作为兼容读取窗口。
4. 先上线只读递归查询和摘要接口，再切换新建、草稿、提交和调整写入路径。
5. 验证历史 O/A 树、跨级指派、草稿版本和进度汇总后，移除前端基于 records 全量过滤树的逻辑。

## 8. 验收标准

- 老板可创建 O-A1/A2/A3 并分别指派多个主管，数据库中只存在一份来源 A。
- 主管只能从真实指派的 A 创建 A11/A12/A13，不能把自己创建的动作伪装成上级来源。
- A11 可继续创建 A111/A112，树路径和来源链路可追溯。
- 员工未获得有效指派时没有可拆解动作；获得指派后只能从对应来源进入编辑。
- 草稿可编辑，已提交节点只读，撤回/调整产生可追踪版本。
- 默认只展开两级，展开下一层不会加载整棵树；“全部展开”可用但不是默认状态。
- 父级进度按权重递归汇总，并展示承接数量、完成数量和异常提示。
- 网络错误、权限不足、来源失效、并发冲突和空数据均有明确反馈，且不丢失当前筛选和编辑上下文。
