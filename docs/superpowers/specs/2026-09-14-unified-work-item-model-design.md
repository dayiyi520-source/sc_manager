# 统一工作项模型设计

## 目标
在不引入模块层、不中断现有业务表和接口的前提下，建立“产品线 → 版本/迭代周期 → 工作项”的统一模型。需求评审通过后原子创建设计、研发、测试三个主任务；研发和测试主任务可继续创建类型化子任务。

## 业务边界
- 每个产品线使用一套统一工作项体系，包含多条工作项记录；分类为需求、设计、研发、测试、缺陷，不按分类建立互不相通的工作项体系。
- 分类下的任务类型由所属产品线自定义，适用于各分类，不限于研发和测试。
- 研发负责人按需创建前端、后端等子任务；接口联调纳入前后端任务。评审通过时不自动拆分这些子任务。
- 测试用例、测试执行等是测试子任务类型，不是一级主任务。
- 设计主任务允许选择“无需设计”并完成。
- 研发验收、产品验收通过当前工作项状态操作完成，不单独创建任务。
- 一个版本对应一个迭代周期，需求只能归属一个版本；已发布版本默认只读。

## 状态、流转和关系
状态分为分类状态、通用状态属性、流转规则三部分。状态定义按产品线+工作项分类配置，状态类别、阶段、初始/终态和成功结束属性统一。每个分类有自己的状态节点和流转路径，在所属产品线中自定义；分类下的任务类型不另建独立流程。流转规则定义起止状态、操作、角色、必填字段、依赖清理要求和自动流转标记。已发布流程版本不可修改，只能新建版本；已使用状态只能停用。

阻塞、等待依赖、逾期是业务状态之外的属性。测试中遇到阻塞仍保留测试中；解除阻塞仅移除标记并记录活动，不跳转业务状态。历史记录只有“已阻塞”且没有原状态时不得猜测原状态。已评审和已验收不能在兼容映射中直接推断为需求整体完成。

子任务仍是统一工作项，通过 parent_work_item_id 表达父子关系，任务类型并不代表父子层级。产品线配置可创建的子任务类型和允许的父子分类组合；创建时校验租户、产品线、分类和启用状态。父子关系不得自关联或成环。已有类型被停用后历史记录仍可读取，但新建任务不可选用；调整配置不能静默改写历史任务的类型和流程版本。

关系表支持 BLOCKS、RELATES_TO、DUPLICATES、PARENT_CHILD、FOUND_DEFECT、REQUIRES_REGRESSION、CONVERTED_TO。只存正向关系，BLOCKED_BY 反向计算；禁止循环 BLOCKS。

父子关系以 parent_work_item_id 为唯一写入来源，关系视图中的 PARENT_CHILD 从该字段派生，不双写。子任务默认属于必须交付的工作；普通参考和后续跟进使用关联关系，不混入完成门槛。前置依赖区分限制开始与限制完成。FOUND_DEFECT 仅说明发现来源，是否阻塞另按缺陷优先级、发生阶段和有效依赖判定。缺陷展示在测试详情的缺陷区域，与测试用例、测试执行子任务分开。

## 自动创建与事务
需求评审通过和三个主任务创建在同一数据库事务内。任意创建失败，需求和三个任务全部回滚；失败只写服务端结构化日志，不进入任务列表。通知发送在业务事务后独立重试，失败不回滚任务。重复提交使用幂等键或唯一约束拦截。

## 聚合规则
需求完成条件：设计完成或无需设计、研发主任务及必要子任务完成、测试主任务及必要子任务通过、P0/P1有效阻塞缺陷为0、配置的产品验收状态操作完成。测试中发现缺陷时测试保持测试中，需求显示阻塞标记；已完成需求后续线上缺陷不回退需求状态。版本可发布条件：版本内需求全部完成且没有作用于该版本的有效阻塞，不新增独立版本验收门槛。

版本完成度按已完成需求数除以纳入版本的需求总数计算，不受子任务拆分数量影响。没有需求时显示零完成度，不据此推断可发布。阶段和处理人允许并行多值，未完成原因需定位到工作项和条件。取消不等于成功完成。

## 兼容迁移
第一阶段新增统一查询/聚合 DTO 和字段映射，不删除旧表。第二阶段新增状态定义、流转、关系、活动记录表。第三阶段将新建流程接入统一服务，旧接口继续返回兼容字段。历史数据按业务表映射为统一工作项读取模型，待运行稳定后再评估主表化。

## 待实现接口方向
- `GET /api/work-items`：跨类型、版本、负责人、状态、阻塞、逾期查询。
- `GET /api/requirements/{id}/summary`：阶段、处理人、完成项、等待项、阻塞项。
- `GET /api/product-lines/{id}/versions/{versionId}/summary`：完成度、可发布判断、未完成原因。
- `POST /api/requirements/{id}/review-approve`：事务内创建三个主任务。
- `POST /api/work-items/{id}/transitions`：按流程规则执行流转。
- `GET/POST /api/work-items/{id}/relations`：维护依赖和关联。

## 验收边界
覆盖重复提交、事务失败、缺负责人、流程版本变更、循环依赖、跨版本依赖、P0/P1阻塞、P2/P3非阻塞、设计无需执行、测试中发现缺陷、线上问题转入和已发布版本只读。

## 首批兼容读取交付边界
- 仅新增读取接口，不改变旧接口、状态写入和数据库结构；服务端使用已存在的需求、设计、研发、缺陷记录。
- 分类键沿用 requirement/design/dev/test/bug。兼容工作项键使用分类加原 ID，避免不同业务表之间的 ID 冲突。
- 独立设计表优先于需求表保留的同 ID 设计副本；独立记录已删除也不恢复旧副本。没有独立副本的历史设计记录保留读取。
- 不通过名称猜测产品线、版本、负责人或任务类型 ID；历史缺少 ID 的关联不自动补齐。
- 测试存储、流程版本、父子交付关系及依赖尚未接入时，返回 limitations；自动完成和可发布资格为 null，表示无法判定，不能解释为允许操作。
- P0/P1 未关闭缺陷只作为潜在阻塞返回，不能仅凭普通关联宣称它已经阻塞需求或版本。
- 工作项列表强制产品线范围并分页；当前阶段按单产品线加载后筛选，后续数据量增长时改为数据库分页与聚合。

## 第二批统一存储与配置
- `t_product_work_item` 承载五类新工作项，包含类型、版本、父子关系、顶层需求、流程、状态、负责人、日期、工时和审计字段；旧数据继续从旧业务表读取，不自动搬迁或双写。
- `t_product_workflow` 保存按产品线及分类隔离的流程版本；definition 为状态节点和显式边的完整 JSON。草稿可按 revision 修改，已发布版本不可修改。新工作项选择最新已发布版本，历史工作项固定原版本。
- 每个流程恰有一个启用的未开始初始状态，所有启用节点从初始节点可达，至少一个成功终态；完成组对应成功结束，取消组不对应成功结束。
- `t_product_work_item_child_rule` 配置允许的父子类型组合；任务类型不代表层级，配置可允许同类子任务。新增子任务只能引用已有父任务，无重新挂接入口，不能产生父子环。版本和顶层需求从父任务继承。
- 沿用 `t_product_line_work_item_type`，补齐测试分类；已被核心工作项或父子规则引用的类型不可删除/换分类，允许停用。历史无类型 ID 的旧任务暂不自动绑定。
- `t_product_work_item_activity` 保存任务创建、流程草稿修改/发布和子任务规则配置活动。普通关联不在本批转化为交付关系。
- 创建接口必须提供 requestId；同一租户、产品线和请求标识重复提交相同内容返回原记录，内容或创建人不同返回冲突。产品线行锁串行化配置与创建，避免类型停用和创建竞争。
- 已发布版本不接收新任务；配置/创建失败不保留任务或成功活动。这里只开放创建与读取，状态执行、评审自动下发及依赖闭环属于第三批。
- 该批不提供线上迁移或页面替换；本机增量迁移为 V20260914.1，保留本地历史 40 项 Flyway 校验，不修复或覆盖历史校验和。
